# Skinner / Pareto Execution Constraint Model

## Date

2026-05-13

## Core Insight

The system must not merely advise people what to do. It must constrain behaviour so the correct action becomes the easiest or only viable path.

## User Historical Method

The user previously required clients to document activity every 15 minutes in a diary.

Weekly, activities were mapped against urgency and importance:

- urgent and important
- not urgent but important
- urgent but not important
- not urgent and not important

This exposed that many operators spent most of their time in the wrong quadrants, avoiding the important work that would move them forward.

This was an early practical insight into Pareto: a small number of important actions drove most progress, while most activity was distraction, avoidance, or low-value noise.

## Behaviour Pattern Observed

Poor or resistant clients would:

- obfuscate
- excuse
- delay
- stay busy in wrong quadrants
- avoid the work that mattered

Good clients could see the evidence and improve.

They learned to focus on important work and say no to distractions.

## Skinner Analogy

B. F. Skinner trained pigeons to select the correct object by removing or constraining incorrect options.

The pigeon appeared brilliant, but the deeper design principle was that it was not allowed to practice failure paths.

## Product Translation

The app must work the same way.

If the user has a declared goal, the system should disallow non-aligned behaviour as much as possible.

The system should not rely on motivation.

It should constrain the operating path.

## Core/Sleeve Implication

Core/Sleeve should eventually become a constrained execution environment:

- user declares destination
- Autopsy tests readiness
- Worksheet defines proof obligations
- Core/Sleeve creates the operating path
- telemetry identifies drift
- distractions and invalid actions are blocked or flagged
- progression only occurs through evidence

## Product Doctrine

Do not merely teach the right thing.

Wire down the wrong things.

## Connection To Pareto

The system must help the operator identify and protect the few important actions that drive most progress.

It must reduce time spent on urgent but low-value distraction.

## Possible Future Module

Execution Diary / Priority Audit:

- capture time blocks
- classify urgency / importance
- identify Pareto actions
- expose avoidance patterns
- connect to worksheet proof
- connect to Core operating cadence

## Guardrail

This should not become generic productivity software.

It must remain tied to declared destination, Autopsy result, worksheet proof, and Core/Sleeve progression.
