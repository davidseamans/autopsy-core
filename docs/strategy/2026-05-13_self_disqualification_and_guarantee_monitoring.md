# Self-Disqualification + Guarantee Monitoring

## Date

2026-05-13

## Core Doctrine

The user must disqualify themselves at any stage if their behaviour, evidence, telemetry, or operating discipline falls outside the agreed pathway.

The system should not argue, rescue, or emotionally negotiate.

It should expose the state clearly enough that the client can say:

`Yes, I knew that was coming. I had it coming.`

## Guarantee Meaning

The guarantee is not primarily numbers on a page.

The guarantee is action, behaviour, discipline, telemetry, and compliance with the agreed operating pathway.

The subscriber declares the destination.

The system monitors whether their operating behaviour remains aligned with that destination.

## Monitoring Challenge

Financial metrics are measurable through P&L, balance sheet, margin reports, and job profitability.

But guarantee protection also requires non-financial operating signals, such as:

- failure to access or use the operating agenda
- failure to maintain required Notion/Core/Sleeve records
- failure to maintain job margins
- disruption in HR or rostering
- missing payroll inputs
- ignored worksheet actions
- repeated drift from required operating rhythm
- evidence gaps
- off-system behaviour

## Pigeon / Constraint Model

The system should constrain the operator toward the goal and make off-path behaviour visible.

It should not try to save every operator from their self-created Titanic.

The system does its best by:

- defining the path
- monitoring drift
- warning early
- requiring correction
- preserving evidence
- withdrawing guarantee support when the operator disqualifies themselves

## Disqualification Events

Possible future guarantee disqualification triggers:

- false declaration
- missing evidence
- ignored retest condition
- operating outside Core/Sleeve controls
- repeated failure to maintain telemetry
- margin breach without correction
- payroll/HR disruption without action
- refusal to follow operating rhythm
- ignored corrective action
- hidden debt/cash issue
- whale-risk breach without mitigation

## Product Principle

Do not make the product emotionally responsible for saving the client.

The system provides structure, monitoring, warnings, and proof gates.

If the operator ignores them, they self-disqualify.

## Core/Sleeve Implication

Core/Sleeve must eventually support:

- operating cadence monitoring
- telemetry capture
- drift flags
- warning states
- correction gates
- guarantee status
- evidence history
- disqualification log

## Guardrail

This must not become punitive theatre.

It must be calm, factual, and evidence-based.

The desired client reaction when guarantee support is withdrawn is:

`That is fair. The evidence was there.`
